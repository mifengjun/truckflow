## 2 产品定位与范围

### 2.1 已确认的产品定位

Truckflow 服务一家物流运营公司及其多个客户公司。客户使用门户询价、下单和查询业务；海外管理人员使用后台处理订单及运营事务。系统不按多家独立物流公司共用的 SaaS 平台设计。

### 2.2 原型体现的业务范围

- 提货来源为 YQN 仓及其他海外仓，派送至 FBA 仓、商业地址和住宅地址。
- 运输方式包含 LTL、FTL、PTL 的选择入口，但尚未分别实现真实报价和履约规则。
- 完整业务链涉及询价、报价选择、下单、运输跟踪、附件、客户资金、应收应付和异常售后。
- 原型以美国地址、USD、英寸和磅为主；知识文档覆盖美国和欧洲。首发国家、运输方式、币种和计量单位需通过 D01 确认。

### 2.3 已确认的首发边界（2026-10-04）

首版美国 LTL、中文界面、USD/lb/in，客户账号由管理员邀请，订单人工审核。报价与承运商下单由运营人工处理。客户采用预付，余额不足不能下单；订单提交时冻结余额，承运商确认接单后扣款，明确拒单解冻，结果待确认保持冻结。充值采用线下转账，财务核验实际到账后入账。

这些规则替代下方及各模块中对应的未决建议。首个真实业务闭环必须包含最小资金模块；真实承运商 API、在线支付和月结不进入本次首发。细化规格见[首版开发规格](首版开发规格.md)。

### 2.4 分阶段交付边界

建议先交付可登录、可隔离客户、可持久化的“客户资料—询价报价—订单—状态与附件”闭环，再按已确认的结算规则接入真实资金。人工操作与承运商 API 接入的先后顺序由 D04 决定。

多租户 SaaS、司机 App、车辆调度、完整仓储库存、报关及干线海空运系统未在当前需求中提出，不纳入本稿的交付范围。客户批量导入、自动提现、GPS 地图和多语言列为候选扩展，不因原型出现文案而默认列入首发。

## 4 用户与权限

客户与管理端两类入口属于原型范围。以下角色细分为建议待确认，作为权限设计草案。

| 角色 | 数据范围 | 建议允许的操作 |
| --- | --- | --- |
| 客户操作员 | 所属客户公司 | 询价、下单、查询本公司订单和地址、提交问题 |
| 客户财务 | 所属客户公司 | 查看账单、资金明细、提交充值或付款申请 |
| 运营人员 | 授权客户和订单 | 代客询价下单、处理履约、轨迹、附件和售后 |
| 财务人员 | 授权财务数据 | 核验到账、出账对账、费用调整和退款处理 |
| 管理员 | 按管理职责授权 | 账号角色、客户状态和基础配置维护 |

一个账号可以被授予多个角色。客户资料与登录用户分开，一个客户支持多个成员；客户能否自行邀请成员、员工是否按客户分组授权，由 D02 确认。

建议目标规则：

- 每次读取、写入、导出、查轨迹和下载附件均验证业务数据归属，不能仅依赖菜单隐藏。
- 客户不能通过请求参数切换为其他客户，也不能自行修改角色、信用额度和余额。
- 员工代客操作记录操作人及目标客户。权限不足时明确提示且不产生业务变更。
- 客户冻结与登录用户停用分别记录。冻结后是否允许查询历史、付款和处理在途订单，由 D03 确认。

## 5 核心业务流程

### 5.1 询价至履约

客户或运营人员填写收发货、货物、包装和服务信息，系统校验后保存询价，返回可用报价。用户选择有效报价并确认订单；系统保存当时的地址、货物、价格及服务快照，按结算规则检查资金或额度，再进入承运商接单和运输流程。

承运商接单成功后记录承运商订单号、追踪号和可用单据；后续更新提货、在途、签收或异常记录。失败或超时时明确显示当前结果，避免用户反复提交造成重复订单。

### 5.2 资金与结算

预付客户的充值经到账核验后入账，订单按约定节点冻结或扣款；月结客户按约定额度与账期形成应收。已扣费用与待收费用分别记录，账单汇总不能再次收取已扣运费。

承运商追加费用进入费用调整流程，记录依据和处理结果；退款与赔付关联原订单和原交易。预付、月结、扣款时点及审批策略属于 D06 至 D08 的决策内容。

### 5.3 售后处理

客户或运营人员关联订单提交问题，运营人员记录沟通、证据和处理结果。涉及退款或赔付时，工单与资金处理分别跟踪；工单关闭不自动等同于赔付到账。

## 6 功能需求

### 6.1 AUTH 账号与认证

依据：原型登录入口；正式认证能力为建议待确认。

- **AUTH-01**：支持邮箱和密码登录、退出与找回密码；建议首发由管理人员创建或邀请客户账号，注册开放策略见 D02。
- **AUTH-02**：登录后按授权进入客户门户或管理后台，未登录不能访问业务数据。
- **AUTH-03**：账号关联客户成员或员工身份，服务端验证身份与角色；会话过期后提示重新登录。

验收：错误密码无法进入；客户 A 通过修改订单、客户或附件标识访问客户 B 的信息时被拒绝；退出后受保护接口不可继续使用已失效的会话。

### 6.2 CUS 客户管理

依据：原型体现；信用与冻结规则建议待确认。

- **CUS-01**：创建、查询和维护客户编号、公司名称、联系人、电话、邮箱及状态。支持名称、联系人、邮箱和状态筛选。
- **CUS-02**：详情关联客户订单、账户与账单；没有资金模块时，不展示模拟资金为实际余额。
- **CUS-03**：冻结、解冻和调整信用额度记录操作人、时间和原因；信用额度与充值余额分别展示。
- **CUS-04**：批量导入为候选扩展，需先定义模板、重复判定和失败反馈；原型只有演示入口。

验收：客户资料刷新后保留；权限不足不能调额；客户状态变更按 D03 的确定策略影响新增业务，并保留历史记录。

### 6.3 ADR 地址与仓库

依据：原型体现；公共与私有资料边界为建议待确认。

- **ADR-01**：维护常用收发货地址，字段建议包含名称、国家、州省、城市、邮编、街道、联系人、电话和地址类型。
- **ADR-02**：客户私有地址仅本客户可用；公共 FBA 仓库及运营仓库由授权人员维护。
- **ADR-03**：询价可选择地址并带入资料；订单保存独立地址快照，后续修改或停用地址不改变历史订单。
- **ADR-04**：支持 YQN 仓和其他海外仓来源。YQN 关联业务单号、ERP 已配货校验属于原型规则意图，实际启用依赖 D05。

验收：客户不能修改公共仓库或他人地址；删除常用地址不使历史订单失去收发货资料。

### 6.4 INQ 询价录入

依据：原型体现；必填和承运约束需结合 D01、D04、D05 定稿。

| 字段组 | 原型字段或选择 | 正式目标中的处理要求 |
| --- | --- | --- |
| 客户 | 客户名称、联系人和电话 | 客户端从身份带出；代客操作验证授权 |
| 运输 | LTL、FTL、PTL | 仅开放实际支持的方式，选择值必须贯穿报价和订单 |
| 提货 | 仓库类型、关联业务单号、外仓地址和联系人 | 补充结构化地址、联系方式和提货日期，来源可追踪 |
| 收货 | 名称、邮编、详细地址、Business 或 Residential | 保存完整地址；按承运商接口要求拆分字段，不静默截断 |
| 商品 | SKU、品名、HS Code、数量、单件重量与尺寸、申报价值、危险品 | 支持多行；数量、尺寸和重量合法，单位明确 |
| 包装 | 不打托、自带托脚、仓库打托；长宽高、重量、数量、托盘重量 | 区分包装数量、商品数量和托盘数量，明确重量是否含托盘 |
| 服务 | Inside、lift-gate、APPT、ROC、WGD、NSR | 仅展示对应承运商支持的服务及条件，费用来源见报价 |
| 其他 | 提货日期、备注 | 校验当地日期及必要的业务限制 |

- **INQ-01**：保存完整询价输入和客户归属，生成可查询的询价编号。
- **INQ-02**：缺失或不合法的字段定位到具体输入项，后端再次校验。
- **INQ-03**：危险品或不支持的线路不得返回可下单的虚假报价；展示不支持或需人工确认的结果。
- **INQ-04**：支持历史询价查看及复制为新询价。重新询价保留原记录，不默认沿用已过期的价格。

验收：不同运输方式和实际填写的货物信息能完整进入报价与订单；刷新可查询历史询价；失败重试不会丢失输入。

### 6.5 QUO 报价与报价记录

依据：多承运商报价为原型体现；价格来源和定价策略见 D04、D09。

- **QUO-01**：显示承运商、服务类型、参考时效、币种、基础费用、附加费用、总额和适用条件。
- **QUO-02**：报价记录来源、有效期及对应的询价版本；下单时再次验证有效性。报价过期需要重新获取。
- **QUO-03**：一家承运商失败时保留其他有效结果，明确区分无可用报价、部分返回和整体请求失败。
- **QUO-04**：询价记录可按状态查询并关联后续订单。是否允许同一询价产生多张订单由 D10 确认。
- **QUO-05**：承运商成本、客户销售价格和加价策略分开管理；客户展示范围由授权与业务政策决定。

验收：篡改前端金额不能改变实际下单价格；过期报价不能直接下单；报价总额可与费用项核对。

### 6.6 ORD 订单管理

依据：原型体现；审核、取消、资金时点等流程见决策清单。

- **ORD-01**：确认页展示客户、地址、货物、包装、提货日期、承运商、服务和费用。提交后返回唯一订单号及当前处理状态。
- **ORD-02**：保存报价和业务快照，重复点击或网络重试只创建一次对应的业务订单。
- **ORD-03**：查询订单号、地址、SKU、客户、仓库、状态和日期；支持分页、详情及授权范围内的导出。
- **ORD-04**：详情包含运输资料、费用项、追踪号、状态历史、附件和关联工单；操作记录标明来源、时间和人员。
- **ORD-05**：创建记录与承运商接单分开反馈。外部超时显示结果待确认，并提供后续状态；不能以固定等待五分钟替代实际结果。
- **ORD-06**：取消和变更为建议补充流程，启用条件、承运商限制、费用和审批按 D10 确认后实现。影响报价的信息修改须重新确认价格。

验收：提交后刷新仍能查到订单；运输信息与确认页一致；重复请求不重复下单；承运商超时后可恢复查询，不重复创建外部订单。

### 6.7 TRK 跟踪与单据

依据：原型体现；实际数据来源见 D04、D11。

- **TRK-01**：通过内部订单号或承运商追踪号查询授权范围内的轨迹。
- **TRK-02**：时间线记录事件、发生时间、地点、来源和最后同步时间；没有新数据时如实说明。
- **TRK-03**：提供实际存在的 BOL、PL、托盘标签和 POD，记录文件来源及可用状态，授权后下载。
- **TRK-04**：承运商查询入口使用配置的链接。地图和 GPS 实时位置只有获得对应数据源后才作为扩展实现。

验收：未生成附件不显示下载成功；他人追踪号不能泄露订单；重复或乱序轨迹不能无依据地把已完成订单退回早期状态。

### 6.8 CAR 承运商管理

依据：原型列表及自营、代理、第三方分类；操作能力为建议待确认。

- **CAR-01**：维护承运商名称、分类、启用状态、支持国家及运输服务。
- **CAR-02**：配置报价、下单、轨迹、单据的接入方式和状态映射；停用后不再提供新报价，历史订单保留关联。
- **CAR-03**：接入凭据仅服务端保存。失败记录能够关联承运商和内部订单，便于人工排查。

验收：只有已接通或有明确人工处理流程的服务可以对外开放；原型中的承运商名称不等同于已建立合作或已经接通接口。

### 6.9 FIN 资金账户与结算

依据：原型体现；以下目标须在 D06 至 D08 确认后启用。

- **FIN-01**：按客户和币种展示账面余额、冻结金额、可用金额、信用额度和收支流水；每个展示值有明确计算口径。
- **FIN-02**：充值申请记录金额、方式、凭证及处理状态。只有经核验的实际到账才增加余额，提交申请不代表到账。
- **FIN-03**：预付订单的冻结、扣款、解冻与退款关联原订单；同一业务事件只入账一次，并发下单不超占可用资金。
- **FIN-04**：月结形成可核对的应收账单，费用项关联订单及调整依据；预付已扣费用在汇总账单中标明已结清。
- **FIN-05**：客户查询、下载本人账单和明细；财务核验付款、处理差异、记录催款结果。通知未实际送达不得显示已送达。
- **FIN-06**：承运商应付账单关联运输成本、附加费用和付款记录，与客户销售价格分开核算。
- **FIN-07**：追加费和反弹项记录订单、原因、金额、凭证、申诉及最终承担方；不能直接覆盖原报价抹去历史。
- **FIN-08**：退款及候选提现功能记录申请、审核、执行、失败和到账结果。是否开放提现、是否接信用卡由 D08 决定。

验收：账单明细与总额一致；充值回调重复到达不重复入账；已扣订单不被账单二次扣费；退款、赔付和费用更正均可追溯。

### 6.10 CLM 客服与异常售后

依据：原型体现；处理权限和服务承诺见 D12。

- **CLM-01**：关联订单提交物流查询、费用咨询、货损、丢失、延误等问题，保存描述和附件。
- **CLM-02**：工单包含待处理、处理中和已完结等状态，记录处理人、沟通记录、证据和结果。
- **CLM-03**：赔付金额与实际资金处理分别记录并关联；客户可查询允许对外展示的进度，内部备注不对客户公开。

验收：提交后可重新查询工单；关闭工单需要处理结果；显示赔付已到账须有对应资金记录。

### 6.11 RPT 报表与导出

依据：原型体现；指标定义为建议待确认。

- **RPT-01**：提供订单数量、状态分布、客户贡献、承运商使用占比及日期趋势。
- **RPT-02**：统一筛选日期、时区、订单状态和币种；订单金额、已收款、应收和收入分别命名，不相互替代。
- **RPT-03**：妥投率、异常率和客单价明确分子、分母及统计时间。原型目标 95% 不直接成为运营承诺。
- **RPT-04**：导出与列表使用相同权限和筛选范围；大批量导出显示任务进度及结果有效期。

验收：同一范围内报表与列表能核对；不同币种不能未经汇率规则直接相加；界面不混用静态趋势和真实统计。

## 7 状态与数据规则建议

### 7.1 状态模型

建议将以下状态分开保存，名称和可执行操作在模块详细设计时确认：

| 对象 | 建议状态 | 说明 |
| --- | --- | --- |
| 询价 | 待报价、已报价、无报价、已过期、已转订单 | 关联报价和订单；部分承运商失败保留各自结果 |
| 下单处理 | 待审核、提交中、已接单、明确失败、结果待确认 | 是否人工审核见 D10；超时不直接判失败 |
| 履约 | 待提货、已提货、在途、已签收 | 异常事件单独记录，不能与下单失败混为一类 |
| 取消申请 | 待处理、已同意、已拒绝 | 正在申请取消不代表承运商已经取消 |
| 资金操作 | 待核验、已冻结、已入账、已解冻、已退款、失败 | 按具体操作使用，不用订单状态推断余额 |
| 工单 | 待处理、处理中、已完结 | 完结与资金到账独立 |

### 7.2 核心业务对象

建议保留用户、客户、成员关系、角色、地址、仓库、承运商、询价、报价及费用项、订单及货物快照、运输记录、轨迹、附件、账户、交易流水、账单明细、费用调整、工单和操作日志。

这是一份业务对象清单，不是数据库建表脚本。一个订单是否允许拆成多个运输单、一个询价是否允许多次下单，须通过 D10 确认后确定关系。

## 8 非功能需求

以下为建议的上线要求，具体容量与量化指标见 D13。

| 方面 | 要求与验证方式 |
| --- | --- |
| 访问体验 | 在大陆实际客户的电信、联通、移动网络和海外管理人员网络上测试登录、查询、下单及附件传输，记录成功率与响应耗时 |
| 数据持久化 | 刷新、重新登录、服务重启后业务记录仍可查询；模拟数据与生产数据明确隔离 |
| 一致性 | 订单与资金关键写入具备原子性；重复请求、重复回调和任务重试不重复产生交易 |
| 数据隔离 | 接口、搜索、导出、附件、轨迹和统计均执行授权；不同客户不能互相看到记录 |
| 可追溯性 | 下单、代客操作、调额、冻结、退款和状态更正记录人员、时间、原因及关联业务 |
| 时间与金额 | 区分物流当地时间和用户展示时区；金额精确计算并携带币种，重量和尺寸携带单位 |
| 交互 | 表单定位错误；列表提供加载、失败、空状态；提交中防重复操作；键盘可完成主要表单操作 |
| 运维 | 失败任务可查询和重试，记录关联编号；配置备份并验证恢复，测试及预览环境与生产隔离 |
| 容量与性能 | 根据 D13 的客户数、订单量、并发和数据保留期设定性能测试，不提前承诺未经验证的时延或可用率 |

## 9 建议交付阶段

以下为建议顺序，不是已确认工期或上线承诺。

| 阶段 | 交付内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| 第一阶段 基础与隔离 | 登录、成员归属、角色、共享 UI、客户与地址资料 | 真实登录、数据持久化、越权测试通过 |
| 第二阶段 询价与订单 | 首发线路及运输方式、报价来源、订单快照、查询、基本履约和附件 | 可完成真实或明确人工承接的订单闭环；仅使用测试数据时不得宣称可生产运营 |
| 第三阶段 资金与结算 | 按确认政策接入充值核验、冻结扣款、账单、退款和追加费 | 资金规则确认，并发、幂等和对账验收通过 |
| 第四阶段 运营完善 | 更完整的承运商自动化、跟踪、售后、统计及导出 | 外部接口、异常处理和统计口径完成验收 |

若首发必须预付下单，第三阶段的最小资金闭环必须提前并入第二阶段，不能在没有真实资金控制时开放相应业务。

## 11 原型差异与开发注意事项

| 原型现象 | 需求处理 |
| --- | --- |
| 任意非空邮箱密码可进入并选择客户 | 只作为演示入口，正式账号由真实身份和成员关系决定 |
| FTL/PTL 可选择，但询价及订单保存为 LTL | 视为原型缺口，正式系统必须保留实际选择且校验是否支持 |
| 下单货物和地址仍使用固定示例值 | 必须使用本次确认信息形成快照 |
| 报价为固定基础费加勾选费用 | 示例金额不导入生产费率；真实定价见 D09 |
| 提交充值申请立即增加余额 | 改为到账核验后入账，申请状态与到账状态分开 |
| 下单扣费后，账单仍可再次扣款 | 明确结算模式和费用结清关联，禁止重复扣费 |
| 地址簿共用，轨迹按全部订单搜索 | 正式查询与维护都必须执行客户隔离 |
| 附件下载、催款及客服提交仅弹出成功提示 | 必须有实际文件、发送结果或工单记录作为依据 |
| 详细地址限制 35 字符、托盘固定规则 | 作为原型中的接口假设，按实际承运商契约确认，不能截断完整业务地址 |
| 固定等待五分钟、客服三十分钟响应、特定追踪号前缀和承运商认证文案 | 不直接采用为系统承诺；由实际接口能力及 D12 确认 |
| 运费知识文档包含参考数字及分类 | 不作为生产算法、法规判断或承运能力保证；以实际业务合同和接口为准 |
