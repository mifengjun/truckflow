## 3 通用业务约束

- 身份由 Supabase Auth 验证，归属与权限从数据库读取；前端传入的客户 ID、角色、金额不作为权威依据。
- 写入时使用当前权限与客户状态；停用成员不能凭旧页面或旧 JWT 继续操作。账号停用策略由 D03 细化。
- 完整地址不静默截断；询价保存结构化地址与联系人，订单冻结快照，常用地址变化不回写历史。
- 货物数量为正整数，重量尺寸为正数并携带单位；危险品与不支持线路进入不可下单或人工确认结果，不伪造可用报价。
- 金额使用 `numeric(18,2)` 与 ISO 币种，HTTP 金额为十进制字符串，计算使用十进制库；重量/尺寸使用 `numeric(12,3)`，日期使用提货地当地日期与 IANA 时区，事件存 `timestamptz`。
- 报价时效不默认作为承诺；报价带来源、完整费用项、询价版本及有效期。有效期由正式来源/运营政策决定，无法确定时不能供生产下单。
- 订单、承运商接单、履约、资金和售后状态分开。操作成功提示必须对应持久化记录或外部确认。
- 业务修改与审计记录在同一事务中保存。数据库事务内不调用承运商网络接口。

| `carrier_submissions` | order_id、external_reference、external_id、状态、attempt、错误摘要 | external_reference 唯一且重试保持；阶段二 |

| `attachments` | 客户、订单、私有对象路径、类型、大小、来源 | 对象路径不是公开 URL；下属归属与订单一致；阶段二/四 |

## 6 服务与数据库访问边界

模块化单体：HTTP/页面 → 已授权业务服务 → repository → Drizzle/Postgres.js。`/api/v1` 使用 Node.js runtime；Server Components 调同一服务。Auth/Storage 用 Supabase SDK，业务写入走同源 API。首版后台的人工报价与回填也是服务操作，不能直接编辑数据库代替业务流程。

业务表置于非 Data API 暴露的 `app` schema，不授予 `anon`、`authenticated` 直接业务 DML。迁移明确撤销默认 grants，业务表启用 RLS，默认拒绝未配置的访问；验证 Data API 确实不可访问。不能用“加了 RLS”声称受 postgres/service_role 直连保护。

服务端使用单独受限数据库角色，仅获所需业务表权限；该服务角色的跨客户读写能力由业务服务独立授权，不冒充终端用户 RLS。Auth 管理凭据仅在邀请/管理入口使用。数据库、Auth 管理及队列 worker 三类权限分开；授权上下文不可由客户端构造。

会话使用官方 `@supabase/ssr` Cookie 集成；验证 claims 后每次解析活跃 profile、成员关系与角色。服务端不单独信任 `getSession()` 返回的用户。`src/proxy.ts` 负责刷新及初步导航，服务层仍是最终授权入口；会话刷新响应不进共享缓存。

Postgres.js 连接选择需验证：官方现已提示 shared transaction pooler 与 pipelining 的兼容风险，单设 `prepare:false` 不解决该风险。阶段一先在测试环境评估 Session pooler + 小连接池（每实例 max=1）与连接总量；迁移独立连接。若需 transaction pooler，先通过并行查询、事务和回滚测试再采用；不使用会破坏事务的 `max_pipeline:0`。此为对原架构连接建议的补充，不视为已完成验证。

迁移唯一历史为 `supabase/migrations`，SQL 与 Drizzle schema 一起更新；运行时不建表。数据库连接使用证书校验 TLS；预览、测试和生产分开配置，CI 不输出连接串。

## 7 订单状态与外部一致性

人工审核已确认。首版由运营领取订单并人工提交，保存操作人和领取时间；记录实际结果后推进状态。以下自动 worker 状态用于后续 API 接入，首版不为人工操作生成自动提交任务。

| 当前处理状态 | 动作 / 结果 | 下一状态 | 限制 |
| --- | --- | --- | --- |
| `pending_review` 待审核 | 核对并批准 | `queued` 待提交 | 有权限、版本一致、资金条件满足；事务写 outbox |
| `queued` | worker 领取并记录提交 | `submitting` 提交中 | 使用稳定 external_reference |
| `submitting` | 承运商确认 | `accepted` 已接单 | 保存实际外部订单号/追踪号 |
| `submitting` | 明确拒绝且确认未创建 | `failed` 明确失败 | 保留依据及原因 |
| `submitting` | 超时、连接中断或未知响应 | `unknown` 结果待确认 | 不自动再次 create |
| `unknown` | query 确认已创建 | `accepted` | 查询同一 external_reference |
| `unknown` | 权威查询确认未创建 | `failed` 或经授权重新排队 | 来源可追溯；查不到本身不等于未创建 |
| `failed` | 核对后重试 | `queued` | 报价/资料变更先重新确认；避免新外部标识 |

worker 在提交后崩溃、lease 超时或队列重复投递，也按未知结果恢复查询；不能盲目重发。承运商不支持幂等或查询时进入人工核实，不自动重试 create。

履约独立使用 `awaiting_pickup`、`picked_up`、`in_transit`、`delivered`；异常另记事件。重复事件去重，乱序轨迹不让已签收退回待提货。取消功能待 D10 确认，不能把取消申请立即等同于取消成功。

下单事务：锁定/校验报价版本、客户归属、有效期及 source_mode → 校验幂等 → 校验并执行资金占用 → 写订单快照、幂等结果与事件 → commit。首版进入人工审核队列，不投递自动承运商提交任务。并发请求通过唯一约束及锁保证一笔业务只生成一次订单。报价与冻结快照不可受后续地址/询价编辑影响。

### 7.1 首版人工流程

1. 客户保存询价后进入待报价；运营读取真实资料，录入承运商、销售金额/费用项、有效期、时效说明及报价依据，成本单独存储。
2. 报价发布后客户比较并确认；修改地址/货物等影响运价的信息产生新版本，旧报价不可沿用。
3. 客户提交订单时服务端检查可用余额，事务处理资金与订单后进入 `pending_review`。
4. 运营核对资料，按 `expectedVersion` 原子领取订单，状态转 `submitting`，记录正在人工下单。重复领取或其他操作员的过期页面返回冲突。
5. 运营回填确认接单、明确拒单或结果待确认。接单要求真实承运商订单号或可追溯确认依据，追踪号尚未生成时如实显示；未知结果不允许重新下单。
6. 回填接单/拒单与对应资金处理在同一数据库事务内执行，避免订单已接单但资金未扣、拒单但未解冻。

报价发布需至少一项真实有效报价；没有适用服务则标记无报价并记录原因。首次发布后新增报价可独立发布，已有被下单报价不得覆盖。通过权限区分录价、发布、审核、回填和财务核验。

### 7.2 已确认的首版资金流程

`available = balance - held_amount`。余额与冻结均为 USD 精确小数；冻结只是占用，不扣账面余额。首版账面余额不得为负。

| 业务事件 | 余额变化 | 冻结变化 | 前提 |
| --- | --- | --- | --- |
| 客户提交充值申请 | 0 | 0 | 上传凭证仅作为待核验证据 |
| 财务确认实际到账 | +到账金额 | 0 | 锁账户及申请；保存到账参考和核验人；同一申请只入账一次 |
| 客户确认下单 | 0 | +订单销售总额 | 锁账户；可用余额足额；与订单创建同事务 |
| 运营确认接单 | -订单销售总额 | -订单销售总额 | 锁订单、账户和 hold；与接单回填同事务 |
| 明确拒单 | 0 | -订单销售总额 | 确认未产生外部订单；与失败记录同事务 |
| 结果待确认 | 0 | 0 | 保持冻结，不自动释放 |

例如余额 1,000.00、冻结 200.00，可用 800.00；创建 360.00 订单后余额仍 1,000.00、冻结 560.00、可用 440.00；接单后余额 640.00、冻结 200.00、可用仍 440.00。

充值申请金额与到账金额不同，财务需记录差异理由并通知客户，不能默认按申请金额入账。退款、追加费用和承运商取消成本尚未确定，先保存问题/处理依据，不自动修改余额；不得以“拒单解冻”替代已扣款订单的退款。

并发下单锁同一账户；流水事件键与 hold 保证重试不重复冻结/扣款/释放。锁顺序统一为订单（如存在）→账户→hold/申请，资金事务失败则全部回滚。明确拒单后的重试必须重新校验报价和可用余额，并再次冻结，不能沿用已释放 hold。

## 8 接口契约

成功格式 `{data, requestId}`；错误 `{error:{code,message,fieldErrors?},requestId}`。未登录 401，权限不足 403，不可访问资源 404，状态/幂等冲突 409，字段校验 422，未配置依赖 503。接口和已登录页面 `Cache-Control: private, no-store`。

写接口校验允许的 Origin 与 CSRF；登录/恢复限流。分页使用稳定 cursor（created_at,id），默认 20、最大 100，客户端排序/筛选值白名单。引用未决业务政策的请求显式拒绝，不能默认放行。

| 接口 | 输入 / 输出重点 | 权限 / 阶段 |
| --- | --- | --- |
| `POST /api/v1/auth/login` | 邮箱密码 → 当前用户；不记录密码 | 匿名、来源与限流；一 |
| `POST /api/v1/auth/logout` | 清 Cookie 并退出当前会话 | 当前身份；一 |
| `GET /api/v1/me` | 验证身份与角色、允许入口；不含凭据 | 当前活跃身份；一 |
| `GET/POST /api/v1/customers` | 客户列表/创建；ID 不作权限凭证 | 管理权限；一 |
| `POST /api/v1/customers/:id/invitations` | 邮箱、允许角色 → 邀请记录 | 管理权限，依赖 D02 与邮件配置；一 |
| `GET/POST /api/v1/addresses` | 公共及本公司列表/新增 private | 客户、授权员工；一 |
| `PATCH /api/v1/addresses/:id` | version、允许字段 → 更新资料 | 本公司 private 或公共维护权限；一 |
| `POST /api/v1/inquiries` | schema_version、运输资料 → 编号/版本 | 客户、授权运营；二 |
| `POST /api/v1/inquiries/:id/quote-requests` | 指定 version → 请求 ID | 归属检查，生产服务配置；二 |
| `GET /api/v1/quote-requests/:id` | 分家状态、有效销售报价、source_mode | 本公司；不含成本；二 |
| `POST /api/v1/orders` | quoteId、version；Idempotency-Key；不接收权威金额 | 客户、代客运营；二，生产依赖资金/定价决策 |
| `GET /api/v1/orders[/:id]` | 筛选列表 / 客户可见快照 | 本公司或员工授权范围；二 |
| `POST /api/v1/orders/:id/approve` | expectedVersion、审核依据 | 运营；二 |
| `POST /api/v1/orders/:id/reconcile` | expectedVersion → 核实任务 | 运营，unknown 可用；二 |
| `POST /api/v1/inquiries/:id/manual-quotes` | version、承运商、销售费用、成本、依据、有效期 | 运营；首版人工报价 |
| `POST /api/v1/quotes/:id/publish` | expectedVersion → 发布销售报价 | 运营；客户 DTO 排除成本 |
| `POST /api/v1/orders/:id/manual-result` | expectedVersion、accepted/failed/unknown、外部依据 | 运营；订单与资金同事务 |
| `GET /api/v1/account` | USD 余额、冻结、可用、流水分页 | 本公司，或授权财务 |
| `POST /api/v1/recharge-requests` | USD 金额、转账参考、私有凭证 | 本公司；创建 pending，不增余额 |
| `POST /api/v1/recharge-requests/:id/verify` | expectedVersion、到账金额、到账依据 | 财务；幂等核验入账 |
| `POST /api/v1/attachments/:id/download` | 授权后短时私有链接 | 归属与可见性检查；二/四 |

邀请跨 Auth 与数据库不是一个事务：先创建待处理邀请记录，再调用 Auth；失败保留可重试状态。重试识别已存在身份，绝不把已有其他客户用户默默迁移。邀请跳转白名单；找回密码统一反馈，避免透露邮箱是否存在。

| 一 基础与隔离 | 环境、迁移、真实会话、客户、地址、审计、正式布局 | 两个客户越权测试；员工范围与停用测试；页面/API/数据库无直连泄漏；刷新持久化；错误无凭据 |
| 二 人工报价与最小预付 | 询价、人工发布报价、私有充值凭证、核验入账、冻结、订单快照 | 同 key 重试只一单；不同 payload 冲突；过期/版本拒绝；成本不可见；重复充值仅一次；并发资金不超占 |
| 三 人工履约与真实启用 | 审核领取、人工下单回填、接单扣款、拒单解冻、未知结果核实、单据 | 重复操作不重复资金；未知结果禁止再次提交；回填与资金原子性；真实试单与外部结果一致；范围/定价/关系限制已定 |
